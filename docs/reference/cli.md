## rigg

Configuration-as-code for Azure AI Search and Microsoft Foundry.

A rigg workspace holds one or more projects; each project owns its resource
definitions (indexes, indexers, skillsets, knowledge bases, Foundry agents,
deployments, ...) as JSON files. Pull, push, and diff operate on projects.

New here? Run `rigg concepts` for the workspace/project model.

## rigg promote

Translate one environment's project tree into another

A→B and B→A are the same operation — the A/B sync + hot-swap workflow. Correlates resources by their file stem (logical id), not their physical (Azure) name, and TRANSLATES rather than copies: every infrastructure reference (storage, identity, model host, function app, key vault, api) is re-pointed at the target environment's binding of the same name, and every reference to a sibling that is physically named differently in the target follows that name. The target keeps its own `name`, the paths its own `x-rigg-pin` annotation lists, and its Web API auth carriers — the source's never cross. Anything rigg cannot decide (an unbound reference, a binding the target lacks) becomes a question instead of a guess. Resources that only exist in the target are left untouched. Always previews the rewiring before writing; `--dry-run` stops there.

`Usage: rigg promote [OPTIONS] --from <FROM> --to <TO> [PROJECT]`

### Arguments

| Argument | Required | Description |
|---|---|---|
| `[PROJECT]` | no | Project to promote (omit when the workspace has exactly one) |

### Options

| Option | Value | Default | Env | Description |
|---|---|---|---|---|
| `--from` | `<FROM>` |  |  | Source environment |
| `--to` | `<TO>` |  |  | Target environment |
| `--dry-run` |  |  |  | Preview only; write nothing. Still runs the online checks (pass `--offline` too for a network-free preview), so it may still ask questions |
| `--offline` |  |  |  | Skip every Azure lookup (candidate lists, Web API auth re-derivation, deployment availability); unresolved items are reported instead |

## rigg migrate knowledge-source

Convert an indexed blob knowledge source (azureBlob) to the explicit searchIndex kind, materializing its Azure-generated pipeline (data source, index, skillset, indexer) as project files

Local-only: writes/rewrites project files; the next `rigg push` applies the change. In-place migration keeps every name — push then REPLACES the knowledge source (delete + recreate), which rebuilds the index from source data (time, ingestion/embedding cost, and the source is unavailable until repopulated). Side-by-side (--rename) creates a parallel pipeline under new names; the old knowledge source keeps serving until you cut over and delete it.

`Usage: rigg migrate knowledge-source [OPTIONS] <NAME>`

### Arguments

| Argument | Required | Description |
|---|---|---|
| `<NAME>` | yes | Knowledge source to migrate |

### Options

| Option | Value | Default | Env | Description |
|---|---|---|---|---|
| `--project`, `-p` | `<PROJECT>` |  |  | Project owning the knowledge source (defaults to the only project) |
| `--in-place` |  |  |  | In-place: keep all names; the next push replaces the knowledge source and REBUILDS its index |
| `--rename` | `<NEW-NAME>` |  |  | Side-by-side: create a parallel pipeline under this new knowledge source name (old one keeps serving until you cut over) |
