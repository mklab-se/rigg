# rigg 2.0 — Scope and principles

**Date:** 2026-09-09
**Status:** Approved direction (Kristofer, 2026-09-09). This document is the
umbrella every other 2.0 spec cites. Decisions recorded here are settled;
open questions live in the individual specs.
**Version:** the result ships as **rigg 2.0.0**. rigg 1.x is already on
crates.io, so 1.0.0 cannot be reused. There is NO backwards compatibility with
1.x workspaces or files; from 2.0.0 on, compatibility is kept.

## 1. What rigg is

rigg makes an **Agentic RAG solution built on Microsoft Foundry and Azure AI
Search** version-controllable as configuration on your computer. Foundry
agents ground on Azure AI Search knowledge bases; Azure AI Search indexes
documents from Azure Blob Storage, optionally enriched by custom REST APIs
hosted in Azure Functions. That is the whole target. rigg does this one thing
and does it extremely well.

The measure of "well" is a three-rung ladder, in order:

1. **Round trip.** Take an existing Agentic RAG solution in Azure, pull its
   configuration, delete the solution from Azure, push the configuration back,
   and get a working solution — indexer runs clean, knowledge base retrieves,
   agent answers.
2. **New environment.** Take that configuration, define a new environment
   (different Search service, Foundry project, storage, functions — or some of
   them shared), and deploy it with rigg's help, authentication included,
   without hand-editing infrastructure values.
3. **Production confidence.** The user updates a protected production
   environment through rigg without hesitation, because rigg showed exactly
   what would change and where before it happened, and refused anything that
   would point production at the wrong infrastructure.

Issue #6 (the automated two-environment lifecycle test) is the executable
form of this ladder and is the acceptance test for 2.0.

## 2. Supported configuration

### In scope

| Service | Resource kinds rigg manages | Notes |
|---|---|---|
| Azure AI Search | data sources, indexes, indexers, skillsets, synonym maps, aliases, knowledge sources, knowledge bases | data plane, stable + preview channels |
| Microsoft Foundry | agents (+ versions), model deployments, project connections, guardrails (RAI policies) | Foundry v1 data plane + Microsoft.CognitiveServices ARM |
| Azure Blob Storage | as **the** data source type for Search (`azureblob`; `adlsgen2` for accounts with hierarchical namespace), as knowledge-store target, as indexer enrichment cache, as managed blob knowledge-source origin | rigg understands every storage authentication and networking form (spec: identity & auth) |
| Azure Functions | as the host of custom Web API skills in skillsets | every authentication form Functions offers out of the box: anonymous, function/host key, Microsoft Entra (Easy Auth); the same forms work against any REST API |
| Supporting | user-assigned managed identities, Key Vault (customer-managed keys; secret source for non-Azure APIs), Microsoft Entra app registrations (for Easy Auth) | wiring only, see §4 |

### Out of scope (removed from the code, not left dormant)

- Data-source types other than `azureblob`/`adlsgen2`: Cosmos DB, Azure SQL,
  OneLake, SharePoint, MySQL, Azure Table, Azure Files. The `cosmos.rs`
  client, the Cosmos knowledge-source wizard, and the corresponding scaffolds,
  registry entries and identity edges are deleted.
- Managed (non-`searchIndex`) knowledge sources as a *target* shape: rigg
  still reads and migrates them (`rigg migrate knowledge-source`), but the
  supported end state is an explicit pipeline.
- Anything rigg does not manage is not modelled: Fabric, Cosmos, SQL, Bing
  grounding, Logic Apps, etc.

Simpler is better: a smaller surface that is complete beats a larger one
that is partly right.

## 3. Principles

1. **No secrets, ever.** rigg never stores a key, SAS, password or token in a
   file, never asks the user to type one, and never prints one. Identity-based
   access is the only supported on-disk form. Where Azure genuinely needs a
   secret at runtime (a function key when Easy Auth is not enabled; an API key
   for a non-Azure REST API), rigg fetches it at push time through the
   operator's own Azure login (ARM `listKeys`, Key Vault) and the file records
   only *where it comes from* (`x-rigg-auth`). Validation rejects key material
   outright.
2. **Auth is two-sided and rigg owns both sides.** Every dependency needs (a)
   a role for a service identity on the dependency and (b) rights for the
   operator to grant it and to manage the target. rigg computes both from the
   configuration *before* any mutation, grants what it can, waits out
   propagation, and verifies end-to-end. A push that will fail for auth is
   refused before it starts.
3. **Environments are infrastructure, declared once.** An environment is the
   named Azure infrastructure a project runs on: Search service, Foundry
   project, and the *dependencies* they reach — storage accounts, model hosts,
   AI services accounts, function apps, identities, key vaults. Bindings are
   declared per environment in `rigg.yaml` (configuration first) or learned
   from what Azure shows (discovery first). Both must be effortless.
4. **Files are physical and self-consistent.** Each `envs/<env>/` tree is a
   complete, literal description of that environment. No templating, no
   overlays, no push-time rewriting of infrastructure values. Bindings are an
   *index* over the files, used to validate them and to translate between
   environments — never a substitute for them. (Exception kept from 1.x:
   `x-rigg-*` annotations, stripped before any PUT.)
5. **Promotion is translation, not copying.** Promote rewrites every
   infrastructure reference and every sibling reference from the source
   environment's physical values to the target's, shows the full rewiring
   before writing, and refuses to guess.
6. **Explain, then act.** Every command shows the plan — what, where, which
   environment, which service, which URL — and asks before mutating. Git is the
   mental model: information before consent, never a blind y/N. Protected
   environments require a typed confirmation that `--yes` never satisfies.
7. **Interactive first, scriptable always.** With flags omitted on a
   terminal, rigg guides. Every guided flow has a flag-complete non-interactive
   equivalent and a machine-readable question protocol so CI and AI agents (the
   MCP server) can drive the same flow.
8. **Explicit deletes, idempotent pushes.** Remote deletion needs `--prune` or
   `delete --remote`. A push of an in-sync project performs zero PUTs. After
   every successful push the server document is read back, normalized and
   written to disk and baseline (canonicalization) — never skipped.
9. **A resource belongs to exactly one project, per environment.**
10. **Latest APIs, from a single table.** Every Azure API version rigg uses
    lives in the registry provider table. The watchdog checks all of them.
    Unknown fields seen on pull are surfaced as a canary.

## 4. Provisioning boundary

rigg **configures and wires**; it does **not provision** infrastructure.
Search services, Foundry accounts and projects, storage accounts, function
apps and key vaults are created outside rigg (portal, Bicep, Terraform).
Issue #6 uses Bicep for exactly this.

rigg **may** perform cheap wiring that is part of making a configuration work,
always after showing what it will do and with confirmation:

- enable a system-assigned managed identity on a Search service or Foundry
  project; create a user-assigned managed identity and attach it;
- create role assignments (tagged in their `description` as rigg-created, so
  rigg can list and remove its own);
- create a blob container that a data source, knowledge store or cache names;
- enable Microsoft Entra authentication (Easy Auth) on a function app,
  including creating the app registration and service principal through
  Microsoft Graph, and assigning a managed identity to it;
- create Foundry project connections and model deployments (these are
  rigg-managed resource kinds).

## 5. Identity, tenancy, tooling

- Operator identity: Azure CLI login (interactive) or service principal /
  workload identity federation (CI). rigg uses the operator's tokens for ARM,
  the Search and Foundry data planes, Key Vault and Microsoft Graph.
- **Multi-subscription and multi-tenant are in scope.** An environment names
  its tenant and subscription; bindings resolve to full ARM ids; token
  acquisition is per tenant and per audience.
- **Microsoft Graph is in scope** for app registrations, service principals
  and app-role assignments (Easy Auth wiring).
- AI features (ailloy) are unchanged by 2.0 and out of scope for this work.

## 6. Workstreams and their specs

In execution order. Each has its own design spec and implementation plan.

| # | Workstream | Spec |
|---|---|---|
| 0 | API refresh — every version to the newest, registry provider table | `2026-09-09-api-refresh-and-currency-design.md` |
| 1 | Environments and infrastructure bindings | `2026-09-09-environment-bindings-design.md` |
| 2 | Promote v2 — translation with rewiring preview | `2026-09-09-promote-v2-design.md` |
| 3 | Identity and auth — doctor v2, operator rights, network, Easy Auth, verify | `2026-09-09-identity-and-auth-design.md` |
| 4 | Interaction model — guided flows, question protocol, onboarding | `2026-09-09-interaction-model-design.md` |
| 5 | Scope reduction — remove Cosmos/SQL/etc. | folded into workstream 0's plan (first, to shrink the surface before touching it) |
| 6 | Acceptance — issue #6 two-environment lifecycle test | tracked in issue #6; the manual `test-complete-enduser-experience` skill is updated alongside |

Workstream 0 goes first so everything else is built on current APIs from
day one. Scope reduction is done inside workstream 0 because deleting code
before upgrading it is cheaper than upgrading and then deleting.

## 7. Compatibility and migration

- rigg 2.0 reads only the 2.0 `rigg.yaml` and project layout. No 1.x
  migration code. The user's live `e2e-test/` workspace (untracked) and
  `samples/` are converted by hand as part of workstream 1.
- Version: `2.0.0`; the changelog gets a single `[2.0.0]` section built
  across the workstreams. Release via the existing `/release major` flow.
- From 2.0.0 on: `rigg.yaml`, the project layout, the `x-rigg-*` annotation
  set, exit codes and `--output json` shapes are stable interfaces; changes
  to them require a major version.

## 8. Non-goals for 2.0

- Provisioning infrastructure (see §4).
- Managing documents or running queries beyond the existing `rigg az`
  operations.
- Sovereign clouds beyond what the existing `endpoint:` overrides already
  allow.
- Backwards compatibility with 1.x.
